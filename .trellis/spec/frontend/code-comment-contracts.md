# Frontend Code Comment Contracts

> React/TypeScript 前端方法的必要注释规则：在开发时同步记录无法从名称和类型直接看出的行为约束。

## 适用范围

- 项目手写的 TypeScript/JavaScript 函数、对象方法、类方法、自定义 Hook、事件处理器、状态迁移函数和测试辅助方法。
- React 组件本身仅在职责、渲染分支或数据来源不显然时需要方法级注释；组件内部的关键回调仍按本规范判断。
- 生成代码和第三方代码不要求补注释；不得通过把业务代码标记为生成代码来规避规则。

## 开发门禁

- 新增或修改前端函数、方法时，开发者必须同步检查并补充必要注释；既有注释与实现不一致时必须一并修正，不得把注释工作推迟到独立补扫阶段。
- 涉及以下任一内容时必须注释：非显然的输入/返回约束、状态变更、副作用、异步时序、错误或回退策略、IPC/持久化字段映射、性能取舍、可访问性交互、平台兼容分支。
- 仅当实现足够直观且名称、类型签名已经完整表达行为时，才可不新增注释；禁止为满足规则添加“处理数据”“点击回调”等复述代码的模板化注释。
- 交付前检查本批新增和修改的方法，确认必要注释已添加或更新，并且注释仍与最终实现一致。

## 注释内容与放置

- 优先使用紧贴方法的简洁中文 `//` 注释，说明最关键的约束、结果或副作用；公共 API 需要被编辑器提示复用时可使用 TSDoc。
- 注释必须描述真实实现，不得虚构缓存实时性、事务性、幂等性、重试、安全校验或错误兜底。
- 对一组职责相同的短小回调可使用一条无歧义的组注释；独立的关键行为必须分别说明。
- 注释应解释“为什么”或隐藏契约，不逐行翻译代码，也不替代准确命名、类型约束和测试。

## 错误与正确示例

错误：

```typescript
// 处理点击。
async function handleOpen() {
  await openProject(project.id);
}
```

正确：

```typescript
// 保留当前选中项；打开失败只显示通知，不提前切换工作区状态。
async function handleOpen() {
  await openProject(project.id);
}
```

无需增加模板化注释：

```typescript
const getProjectName = (project: Project) => project.name;
```

## 验证要求

- 代码审查必须覆盖本批新增和修改的方法，并核对注释与最终实现、类型和错误路径一致。
- 修改行为后同步更新相邻注释；过期或误导性注释视为缺陷，不得以保留历史说明为由继续存在。
- 类型检查、Lint 和测试用于验证实现，但不能替代必要注释检查。
