# Backend Code Comment Contracts

> 面向 AI 开发的后端函数注释规则：以最少上下文说明真实行为，同时保持可执行代码不变。

## 适用范围

- 项目手写 Rust 函数、方法、trait 方法、私有实现、`cfg` 分支及测试函数。
- 后端资源脚本、构建/发布/安装脚本，以及直接验证后端或跨进程协议的测试辅助函数。
- Rust 字符串内生成的 PowerShell、Shell、JavaScript、TypeScript 等程序；此类函数使用宿主侧普通注释说明，除非任务明确允许改变生成文本。
- 生成代码、第三方代码和任务归档中的审计工具不属于产品源码；排除时必须在覆盖清单中写明来源和理由。

## 开发门禁

- 新增或修改后端函数、方法时，开发者必须同步检查并补充必要注释；既有注释与实现不一致时必须一并修正，不得把注释工作推迟到独立补扫阶段。
- 非显然的输入约束、返回语义、状态变更、外部 I/O、错误传播、并发/异步时序、安全边界或兼容分支至少说明其中最关键的一项。
- 仅当实现足够直观且函数名、类型签名已经完整表达行为时，才可不新增注释；代码审查时必须确认省略不会隐藏业务约束或副作用。
- 交付前检查本批新增和修改的方法，确认必要注释已添加或更新，并且注释仍与最终实现一致。

## 注释内容

- 使用简洁中文普通行注释 `//` 或脚本对应的普通注释语法，说明输入约束、主要结果、重要副作用或错误传播中最有辨识度的部分。
- 注释必须以实现为依据；不得把路径拼接写成目录边界验证，不得把缓存状态写成实时探测，也不得虚构事务性、幂等性、超时或安全保证。
- 不复述函数名，不为增加字数堆叠模板化语句。相邻的一行小回调可由一条明确的组注释覆盖，前提是职责相同且覆盖关系无歧义。
- 保留已有有价值的文档注释；新增普通注释不得改变 Rust doc attribute、宏输入或生成脚本文本。

## 放置规则

```rust
// 校验请求标识后构造隔离的结果文件路径。
pub(crate) fn result_path(request_id: &str) -> Result<PathBuf, String> { /* ... */ }

// 将命令暴露为 Tauri IPC，保持属性与函数相邻。
#[tauri::command]
pub(crate) async fn run_command() -> Result<(), String> { /* ... */ }
```

- 注释紧贴函数；函数带连续单行属性时，注释放在属性组之前，避免破坏依赖属性邻接的源码契约测试。
- 内嵌程序的宿主注释应点名内嵌函数及行为，例如“内嵌 `Decode-Base64Utf8`：将 Base64 字节解码为 UTF-8”；不得仅写“生成脚本”。

## 等价性验证

- Rust：用语法感知清单比较注释前后的属性、签名、函数体 token 和未展开宏；diff 只允许新增普通注释，必要时只删除空行。
- JS/TS：解析前后源码并比较去注释后的 AST；统一 CRLF/LF 物理换行后再比较，但不得规范化字符串内容或调用结构。
- Shell/PowerShell：运行只读语法解析，并将移除本批新增注释后的源码与基线逐字节比较；不得以运行安装器、真实 SSH、PTY、剪贴板或网络流程代替静态等价证明。
- 编译和测试用于证明集成可用，不替代覆盖清单；平台专属和高副作用场景必须明确报告未执行。

## 错误与正确示例

错误：

```rust
// 处理数据。
fn process(data: &[u8]) { /* ... */ }
```

正确：

```rust
// 按帧大小上限拆分序列化响应，写入失败立即停止后续帧。
fn write_chunks(data: &[u8]) { /* ... */ }
```
