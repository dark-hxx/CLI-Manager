# 修复 cc-connect 多平台配置校验冲突

## Goal

修复首次配置飞书、企业微信等平台时，被隐藏且空白的默认 Telegram 配置阻断保存的问题；统一多平台启用状态、前端校验提示和后端平台化错误，并覆盖全部已支持平台组合。

## Requirements

- 首次打开远程连接设置时，不得把未填写允许用户 ID 的 Telegram 作为已启用平台。
- 平台下拉框仅负责切换当前编辑对象，不得隐式改变已经有效配置的平台。
- 设置页必须展示全部已启用平台，避免其他平台的状态被下拉框隐藏。
- 保存时必须校验所有已启用平台；错误需要明确指出 Telegram、飞书、微信或企业微信中的具体平台。
- Telegram、飞书、微信、企业微信必须复用同一套多平台校验与错误定位流程，不做单平台特判修补。
- 微信扫码授权的既有隔离行为与历史单平台 Profile 迁移必须保持兼容。
- 新增用户可见文案必须同时提供 zh-CN 与 en-US。

## Acceptance Criteria

- [x] 全新配置选择飞书并启用、填写有效 `ou_` open_id 后，可以保存，不受空白 Telegram 配置阻断。
- [x] 全新配置选择企业微信并启用、填写有效 UserID 后，可以保存。
- [x] 同时启用多个有效平台时可以保存并保持全部启用状态。
- [x] 任一已启用平台为空、包含通配符或格式错误时，保存失败且提示中包含具体平台名称。
- [x] 未启用平台的空白草稿不参与保存校验。
- [x] 历史单平台 Profile 仍迁移为一个已启用平台，微信授权流程不受影响。
- [x] TypeScript 构建与 Rust 相关测试通过。

## Notes

- 根因：前端全新 Profile 将空白 Telegram 标记为已启用，而平台选择器只切换编辑对象；Rust 保存边界会校验全部已启用平台并返回无平台归属的通用错误，因此正确的非 Telegram 配置被隐藏的无效状态阻断。
- 修复落点位于 Profile 初始状态、设置页多平台可见性和 Rust 保存校验边界，而不是飞书凭证或 cc-connect 源码。
